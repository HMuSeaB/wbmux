# 设计说明

## 要解决的问题

WorkBuddy 有两个发行版：国内版（`www.workbuddy.cn`）和国际版（`www.workbuddy.ai`）。
它们是同一个 Electron 应用的两个构建，但安装目录、数据目录、账号体系全部独立，
同时使用的人只能装两份。

两份安装的**程序本体高度重合**（见 [EVIDENCE.md](EVIDENCE.md) 的哈希比对），
真正的差异集中在产品配置里。也就是说，多装的那 1.3 GB 里，绝大部分是同一份
Electron 运行时和同一份应用包。

`wbmux` 的目标是：**让同一份安装按需连接不同的后端**，从而省掉重复的那一份。

## 机制

客户端在决定"我是哪个产品、连哪个后端"时，读的是产品配置。而这份配置有
两条外部覆盖通道，**优先于安装包内自带的 `product.json`**：

| 环境变量 | 含义 |
|---|---|
| `ACC_PRODUCT_CONFIG_PATH` | 指向一个 `product.json` 文件路径 |
| `ACC_PRODUCT_CONFIG_V3` | 直接内联 JSON（与上者互斥） |

`wbmux` 走的是第一条：读取宿主安装自己的 `product.json`，只覆盖决定后端的
少数字段，生成一份合并配置，再把路径通过环境变量交给客户端。

这个机制不是猜的，是从发布产物里读出来的，过程见 [EVIDENCE.md](EVIDENCE.md)。

## 关键设计决定

### 不随包分发官方 `product.json`

最省事的做法是把两套官方配置都打进二进制，切换时直接整份写出。`wbmux`
**没有**这么做，原因是：

- 官方配置是腾讯的产物，随包分发有许可风险；
- 配置会随版本变化，内置的副本必然过期，用户会拿到一份"去年的配置配今年的客户端"。

改为只内置**后端描述符**——若干 URL 与标识符，都是接入信息而非配置文件。
运行时读用户自己的安装，因此天然跟随官方升级。

### 最小补丁，而不是整体替换

只改写决定后端的字段：

| 字段 | 说明 |
|---|---|
| `endpoint` / `stagingEndpoint` | 主服务地址 |
| `officialEndpoints` | 允许的端点白名单 |
| `dataFolderName` | 数据目录名 |
| `isOversea` | 区域标志（切国内版时**删除**该字段，而非置 false） |
| `authentication.id` / `.label` / `.attributes.platform` | 认证标识 |
| `authentication.attributes.*Domain` | 四个域名列表 |

其余字段一律原样保留，包括：

| 保持原样的字段 | 原因 |
|---|---|
| `productName`、`applicationName`、`win32ExecutableName`、`urlProtocol` | 宿主身份。改掉会引发互斥检测、协议注册错乱、任务栏分组异常 |
| `updates`、`updateUrl` | 避免国内版被引导去拉国际版安装包 |
| `smhHost` | 区域性的安全遥测端点 |
| `models`、`prompts`、`agents`、`tools`、`productFeatures`、`config` | 与后端选择无关，且官方随时可能增删 |

实现上刻意用 `map[string]any` 而非结构体承载配置：结构体必然漏字段，
而漏字段意味着静默丢失。解析时开 `UseNumber()`，否则配置里的大整数标识符
会在重新序列化时变成科学计数法并丢精度。

### 数据目录跟随目标后端

切换后端时把数据目录也一并切到目标档位的目录（`~/.workbuddy` ↔ `~/.workbuddy-ai`），
通过 `--user-data-dir` 传入。

两套后端的账号体系互不相通。若共用一份 profile，来回切换会互相冲掉登录态——
而"来回切换"正是本工具的主要用法。各自独立后，行为与"装两份"时一致。

### 不修改安装目录

只设环境变量、只写自己的缓存目录（`~/.wbmux/`）。安装目录零改动，
出问题删掉快捷方式即回到原状。这也意味着卸载 `wbmux` 不会有残留。

### 定位安装：分层策略

客户端可能装在任意位置。实测这台机器上：

- 国内版装在 `D:\Tools\WorkBuddy`，靠**数据目录线索**找到——客户端在把
  自己注册为 Office 文件关联时，会往 `settings.json` 写一条含主程序绝对
  路径的标记；
- 国际版装在 `D:\WorkBuddyAI`，**上面那条线索不存在**（国际版不注册
  Office 文件关联），只能靠**注册表**找到。

因此探测按可靠性分层，逐层惰性求值：

1. **显式配置**——用户用 `--exe` 指定。权威，不存在就硬失败，绝不悄悄退回
   后面的策略（否则会出现"指定了 A 却启动了 B"）；
2. **数据目录线索**——客户端自己写下的路径；
3. **注册表**——遍历 HKCU / HKLM（含 32/64 位视图）的 Uninstall 项。
   最不受安装位置影响，也最权威；
4. **常见安装目录**——环境变量推导的位置，加上盘根探测；
5. **PATH**。

两处易错点已在代码与测试中固定下来：

- 产品名匹配**不能只做前缀**。`WorkBuddy` 是 `WorkBuddy AI` 的前缀，
  只做前缀判断会把国际版的注册表记录算到国内版头上；
- 路径推断要**长串优先**。国内版主程序名 `WorkBuddy` 是国际版
  `WorkBuddyAI` 的子串，按短串优先会把国际版路径判成国内版。

### 依赖未公开机制，因此必须能自检

这套机制依赖客户端未公开的配置加载行为，官方改版可能静默移除。
静默失效是最坏的结果：用户以为切换成功了，实际连的还是原后端。

因此 `wbmux doctor` 会直接扫安装包，确认两个关键标记仍然存在：

- `ACC_PRODUCT_CONFIG_PATH`——读取覆盖文件路径的环境变量名；
- `MUTUALLY_EXCLUSIVE_ENV_GROUPS`——声明这两个通道互斥的那行源码。
  它的存在说明双通道机制仍然成立。

扫描用流式分块（4 MiB）并在块间保留 `maxLen-1` 字节重叠，避免标记跨块时漏检。
实测 300 MB 级的 `app.asar` 约 150–200 ms。

`wbmux run` 则在启动前回读生成的配置，确认 `endpoint` 真的等于目标后端。
这一步几乎不花时间，却能挡住"补丁字段名写错"这类静默失败。

### 为什么是 Go

- **单二进制**：零运行时依赖，非技术用户下载即用。Rust 同样能静态链接，
  但 Go 的交叉编译与 `-ldflags` 注入版本信息更省事；
- **零第三方依赖**：目前 `go.mod` 里没有任何 `require`。注册表读取这类
  平台功能直接用 `syscall` 调 `advapi32`，不为一个探测功能引入
  `golang.org/x/sys`。依赖越少，供应链风险越小，也越容易审计。

### 图形界面：内嵌网页，而不是原生窗口

界面是一份 HTML，用 `//go:embed` 编进二进制，启动时只在 `127.0.0.1`
开一个本地服务，再用系统浏览器打开。

考虑过原生窗口库（`webview_go` 之类）。实测下来它并不大——一个最小示例
编译出 2,288,640 字节、无额外 DLL，因为它调用系统 WebView2 运行时而不是
自带浏览器引擎。真正的问题不是体积：

- **cgo 会毁掉交叉编译**。本项目靠一个 ubuntu runner 产出全部平台，
  原生窗口库需要各平台各自的 C 工具链与系统库（Windows 上还要 MSYS2 gcc）。
  这对贡献者是一道硬门槛。
- **它会把"零第三方依赖"这条线破掉**。引入一个 C 依赖之后，
  可审计性这个卖点也就没了。

内嵌网页的代价是明确的：`net/http` 会带进 `crypto/tls` 与 `crypto/x509`，
二进制从 2.5 MB 涨到 6.3 MB（压缩后 1.1 MB → 2.6 MB）。换来的是
零依赖、交叉编译、以及命令行与界面共用同一条逻辑路径。

界面看起来像个本地程序，靠的是 Edge / Chrome 的 `--app=` 模式：
没有地址栏、没有标签页、任务栏里是独立一项。没有 Chromium 系浏览器时
退回系统默认浏览器，功能不受影响。

安全上有两点是硬约束，不是可选项：

- **只监听回环地址**。这个服务能启动本机进程，暴露到局域网等于把机器
  交出去。因此 `--addr` 传非回环地址是直接拒绝，不做"警告后放行"。
- **一次性令牌**。任何网页都能向 `127.0.0.1` 发请求，所以每次启动生成
  一个随机令牌写进访问地址，接口校验它——挡住本地 CSRF。首页同样校验，
  否则可以被嵌进 iframe 里诱导点击。

进程生命周期也做了兜底：页面每 60 秒发一次心跳，30 分钟无访问则自行退出。
双击启动时进程没有控制台窗口，少了这个兜底，用户关掉标签页后只能去
任务管理器里收拾残留进程。

## 已知限制

- **不做历史同步**。两个后端对应不同账号体系（国内受《个人信息保护法》
  约束，国际受 GDPR 约束），会话数据无法跨后端复用。手动搬运会话文件
  技术上可行，但两边的内核版本并不一致，风险自负。
- **不能同时运行两个后端**。同一个安装目录、同一份 `app.asar`，
  `wbmux` 一次只切换出一个后端。
- **macOS / Linux 未实测**。探测逻辑已按平台分支编写并通过交叉编译，
  但只在 Windows 上做过真机验证。
- **自动更新会覆盖宿主安装**。升级后 `wbmux` 需要重新生成配置——实现上
  每次启动都重新生成，因此这一点无需用户干预；但升级若改动了配置格式，
  需要重新跑 `doctor`。
