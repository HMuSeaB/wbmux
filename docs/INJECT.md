# 把面板挂进 WorkBuddy（悬浮胶囊）

`wbmux gui` 运行时，会往 WorkBuddy 窗口的顶栏右侧挂一个小胶囊「● wbmux 180k · 空闲」。
点它展开一个 400×600 的紧凑面板：上次请求/速率/今日用量、客户端状态、注入模型、
双开、重启、端点复制（默认折叠），以及**最近 5 条请求**——模型、上次请求、
速率、多久前、成败、来源（网关/国内直连/国际直连），一眼看出刚才那条走的哪个模型、有多快。

胶囊上那行数字是常驻仪表，每 3 秒巡检一次（文本没变时不再重复推送，省一次 CDP 往返；刚重注入的胶囊除外）：

| 字段 | 含义 | 数据来源 |
|---|---|---|
| `180k` | 上次请求的大小（prompt tokens）。**超过 256k 转黄、512k 转红** | 网关审计 |
| `212/s` | 最近一次流式请求、首字之后的平均生成速率 | 网关审计 |
| `空闲` | 超过 120 分钟没有新请求；30–120 分钟显示旧值 +「xx 分钟前」，不着色——旧数据不丢，也不冒充"现在" | — |
| `今日 42M` | 当天累计 token；为 0 时整段省略 | 网关审计日度汇总 |

> 口径说明：这是**请求级快照**，不是实时流式计数。一次请求结束后才落记录，
> 所以 `212/s` 表示"上一次请求有多快"，不是"此刻正在流多快"。真·实时速率要改
> SSE 转发链路，暂未做。

整个过程**不改客户端任何文件**：只连客户端自己开出的本地调试端口（CDP），
在渲染层插两个 DOM 节点。刷新窗口就没了。

---

## 它什么时候会显示

同时满足两个条件，3 秒内出现：

| 条件 | 怎么满足 |
|---|---|
| **wbmux 在跑** | 启动 `wbmux.exe gui`（托盘常驻）。它每 3 秒巡检一次调试端口 |
| **客户端带调试端口启动** | **从 wbmux 里启动客户端即可**（面板按钮 / 「双开两侧客户端」/ `wbmux run`）——启动参数里已自动带上 `--remote-debugging-port`。客户端本来就在跑、又不是 wbmux 启动的，才需要用 `tools\windows\restart-workbuddy-cdp.bat` 再拉一次 |

端口按档位分配：国内版 `9222`、国际版 `9223`，双开不打架。端口被别的程序占用时
wbmux 会**自动跳过**这个参数——注入是附加功能，不能反过来挡住客户端启动。

缺一个就不显示：

- 只开了 wbmux、客户端用**普通快捷方式**启动 → 不显示（客户端没开调试端口，wbmux 连不上）
- 客户端带了端口、但 wbmux 没开 → 不显示（没有人去注入）

> 为什么必须带调试端口：CDP 是 Chromium 的调试协议，只能在进程启动时启用。
> 已经在运行的客户端没法临时打开——这是 Chromium 的限制，不是 wbmux 的选择。

## 第一次用：两步

```text
1. 启动 wbmux.exe gui

2. 直接用它启动客户端：面板里点「重启国内客户端」，或「双开两侧客户端」，
   或命令行 wbmux run cn —— 启动参数里自动带上调试端口

   之后 3 秒内，客户端顶栏右侧出现「● wbmux」胶囊
```

只有一种情况需要额外动作：**客户端已经在跑，而且不是从 wbmux 启动的**。
这时它没有调试端口，用 `tools\windows\restart-workbuddy-cdp.bat` 拉一次即可
（之后都从 wbmux 启动，就不用再碰这个脚本了）。

脚本参数（备用）：

| 参数 | 作用 |
|---|---|
| 无 | 重启国内版（`~/.workbuddy/app`），端口 9222 |
| `-Intl` | 重启国际版（`~/.workbuddy-ai`），端口 9223 |
| `-Port 9333` | 自定义调试端口 |
| `-Exe "D:\path\WorkBuddy.exe"` | 客户端不在常见安装位置时手动指定 |

## 胶囊的行为

| 情况 | 结果 |
|---|---|
| 点击胶囊 | 展开/收起面板 |
| 点面板外面、按 Esc | 收起 |
| 刷新页面（Ctrl+R） | 胶囊消失，**3 秒内自动回来** |
| 重启客户端（仍带端口启动） | 同上，自动回来 |
| 换新版 wbmux（面板脚本升级） | 自动替换成新版，弹层 iframe 也会强制重载（地址带版本参数） |
| wbmux 退出 | 胶囊**留在原地**，但面板打不开（服务没了）；重新启动 wbmux 即恢复 |

最后一条是当前实现的已知限制：清理残留元素需要 wbmux 还活着才能做。
看到胶囊点不开，先确认 wbmux 是否在跑。

## 不显示时怎么排查

按顺序查，一般三步内能定位：

```text
① 调试端口通吗
   curl http://127.0.0.1:9222/json/version
   返回 JSON（含 "Chrome/..."）→ 端口正常，往下走
   连不上 → 客户端不是带端口启动的，用 restart-workbuddy-cdp.bat 重启

② wbmux 在跑吗
   任务管理器里有没有 wbmux.exe；或看 ~/.wbmux/run.json 是否存在
   没有 → 启动 wbmux.exe gui

③ 手动注入一次，看报错
   wbmux.exe inject
   成功会打印「面板已注入 WorkBuddy 顶栏右侧」和注入标记
   失败会直接说原因（端口不通 / 没有可注入的页面 / 界面还在加载）
```

补充：

- 端口被别的程序占了：`restart-workbuddy-cdp.bat -Port 9333` 换一个，然后
  `wbmux inject --cdp 9333` 同样指定端口
- 客户端版本升级后胶囊不出现，先跑一次 `wbmux inject` 看是否有异常；
  注入只依赖 `document.body` 和固定定位，不依赖客户端内部结构，一般不受升级影响

## 它是怎么工作的

```text
wbmux gui
  └─ 守护协程（每 3 秒）
       ├─ 连 127.0.0.1:9222/json/list 找 renderer/index.html
       ├─ Runtime.evaluate 读页面里的注入标记
       │    标记 = 面板版本 | 面板地址
       │    - 客户端重启 → 标记没了 → 重注入
       │    - wbmux 重启换令牌 → 地址变了 → 用新地址重注入
       │    - 面板脚本升级 → 版本号变了 → 替换
       └─ 不一致就注入：胶囊 + 弹层 iframe（指向 /embed）
```

几个实现上的坑（改代码前值得读）：

- 顶栏是 Electron 的窗口拖拽区，注入元素必须显式 `-webkit-app-region: no-drag`。
  否则**真实鼠标点不动**，而 CDP 派发的模拟点击却能过——这个差异排查了很久。
- 弹层关闭时必须是 `display:none + pointer-events:none`。只设透明度会留一块
  "隐形玻璃板"，把下面的编辑区鼠标事件全挡掉。
- 面板页是 `/embed`（紧凑单列），不是主界面。主界面是侧边栏 + 十几个页面的
  桌面后台布局，塞进 400px 弹层里没法看。

---

## 安全边界

- 调试端口只绑定 `127.0.0.1`，局域网访问不到
- 只读渲染层：不读写客户端文件、不改请求、不碰账号凭据
- 面板里显示的数据全部来自 wbmux 自己的本地接口（`/api/*`，带一次性令牌）
- 想彻底去掉：关掉 wbmux，刷新客户端窗口，胶囊和面板一起消失
